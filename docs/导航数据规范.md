# NavSphere 导航数据规范

> 适用范围：本文档仅规范 `src/navsphere/content/navigation.json` 的数据层编辑约定（书签增删改、分类调整、字段含义）。
> 不涵盖站点功能、UI/样式、原有技术架构的改动。任何数据变动均不改变既有功能与用户体验。

## 一、数据结构

导航数据为两级嵌套结构，自 `navigation.json` 顶层的 `navigationItems` 数组开始：

- **一级分组（category）**：共 12 个，作为页面主导航分区。
- **子分类（subCategory）**：隶属于一级分组，由原 63 个分类重组而来，共 63 个。
- **叶子条目（item）**：具体的书签链接。

实测数据基准（随 Issue #1 / REQ 落地后）：

| 层级 | 数量 |
|---|---|
| 一级分组 | 12 |
| 子分类 | 63 |
| 叶子条目 | **588** |

### 各级字段

**一级分组 / 子分类**

- `id`：唯一标识，用作锚点定位（原 63 分类 id 保留）。
- `title`：显示名称。
- `icon`：图标。留空时前端按"自动 favicon"策略渲染（见第三节）。
- `description`：分组描述，可留空。
- `enabled`：是否启用。`false` 时该层级整体隐藏（见第三节）。
- `items`：叶子条目数组。
- `subCategories`：子分类数组（仅一级分组有）。

**叶子条目（item）**

- `title`：书签名称。
- `description`：说明文字，可留空或填写使用提示。
- `href`：目标链接。必须为标准 `https://` 单协议头，禁止出现 `https:https://` 等重复协议头。
- `icon`：图标。留空 = 自动 favicon。
- `enabled`：是否启用。`false` 时该条目隐藏（下架，可恢复）。

## 二、编辑纪律（数据层红线）

1. **只动数据，不碰功能**：所有变动仅限于 `navigation.json` 的字段值增删改，禁止修改页面组件、样式、路由、构建配置（`.npmrc` 受控，勿删）。
2. **走审核闭环**：需求先以 GitHub Issue 提出（标签 `type/data`），经评估后由维护者改动并推仓；推仓后执行"三层验证"（GitHub 文件为新值 → CF 构建 success → 站点在线）。
3. **保留历史、可恢复**：下架条目用 `enabled=false` 而非物理删除（见 REQ-09）。
4. **不引入重复收录**：同一站点避免多条重复条目；同名多域名需在 description 注明区分。
5. **描述质量**：description 用于辅助说明，宜简洁明确，必要时给出使用提示（如无法直接打开的页面注明"微信搜索小程序"等）。

## 三、关键字段约定

### 1. icon 留空 = 自动 favicon（REQ-03）

- 当 `icon` 字段为空字符串或缺失时，前端自动抓取目标域名的 `favicon.ico` 作为图标（已实施的策略 A）。
- 仅当自动 favicon 不可用（如 CDN 无图标、内网站点）时，才显式填写 `icon` 为图标 URL。

### 2. enabled = 下架 / 隐藏手段（REQ-09，零代码采纳）

- `src/lib/data-loader.ts` 的 `filterNavigationData` 已在三级（category / subCategory / item）按 `enabled !== false` 过滤。
- 因此将任一节点的 `enabled` 置为 `false` 即可隐藏该节点 **且保留数据**，随时可改回 `true` 恢复，替代物理删除。

### 3. 统计口径：712 vs 588（REQ-08）

- 文档早期/历史口径曾记载"712 书签"，该数字为 **含父级 / 子分类计数的虚高历史口径**，并非叶子条目真实数量。
- 当前实测叶子条目为 **588**（12 一级 / 63 子分类）。
- 后续文档与汇报统一以 **588（叶子条目）** 为准；如引用"712"须注明其为历史含层级计数口径。

## 四、更新方法

1. **后台编辑**：访问 `/admin`（需 GitHub 登录授权），在可视化编辑器内增删改后保存（经 GitHub API 写回 `navigation.json`，需重新部署生效）。
2. **直接改 JSON**：编辑仓库内 `src/navsphere/content/navigation.json`，提交后由 Cloudflare Pages 自动构建部署。
3. **投稿功能**：站点提交表单 → `/api/submissions` → 用 `GITHUB_PAT` 在仓库建 Issue（需 `GITHUB_OWNER` / `GITHUB_REPO` / `GITHUB_BRANCH` 配置齐全，且 `_worker.js` 已透传 `GITHUB_PAT`，见 commit `29332710`）。
